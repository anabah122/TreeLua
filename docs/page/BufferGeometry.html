BufferGeometry

Vertex data for one primitive. three.js stores attributes in typed arrays and uploads them to the GPU itself; LÖVE already owns that step, since the importers build a love.Mesh per primitive with the vertex format declared in importer.common. So this class holds that love.Mesh plus the raw vertex/index tables the importer produced, and offers the handful of three.js methods that make sense on top of them.

Constructor

BufferGeometry(entry)

Built either from an importer entry or by one of the generators in three/geometries/, which fill the same fields. entry is optional and defaults to {}.

Methods

.isBufferGeometry()

Returns true.

.computeBoundingBox()

Computes and caches the axis-aligned bounds from .vertices.

.computeBoundingSphere()

Computes and caches a bounding sphere centered on the bounding box's center, radius fit to the farthest vertex. Computes the bounding box first if it isn't cached yet.

.getAttribute(name)

Looks up a named entry in .attributes, or nil.

.setTexture(tex)

Sets the texture on the underlying love.Mesh, if any.

.dispose()

Drops the .mesh reference. three.js frees GPU buffers here; LÖVE meshes are garbage collected instead, so this exists mainly so teardown code reads the same across both.

Differences from three.js

  • No typed-array attribute system (setAttribute, BufferAttribute, morph targets, groups). Vertex data lives in a plain Lua table plus a love.Mesh built by the importer; getAttribute only reads a flat name-keyed table, it does not construct three.js's BufferAttribute objects.
  • .dispose() just drops the reference — there is no GPU buffer to explicitly free.

BufferGeometry

Вершинные данные одного примитива. three.js хранит атрибуты в типизированных массивах и сам загружает их на GPU; в LÖVE этот шаг уже выполняется — импортёры собирают love.Mesh для каждого примитива с форматом вершин, объявленным в importer.common. Поэтому этот класс хранит этот love.Mesh плюс сырые таблицы вершин/индексов, которые произвёл импортёр, и предоставляет ту горстку методов three.js, которые имеют смысл поверх них.

Constructor

BufferGeometry(entry)

Строится либо из записи импортёра, либо одним из генераторов в three/geometries/, которые заполняют те же поля. entry необязателен, по умолчанию {}.

Methods

.isBufferGeometry()

Возвращает true.

.computeBoundingBox()

Вычисляет и кэширует границы по осям из .vertices.

.computeBoundingSphere()

Вычисляет и кэширует ограничивающую сферу с центром в центре ограничивающего бокса, радиус подгоняется под самую дальнюю вершину. Сначала вычисляет ограничивающий бокс, если он ещё не закэширован.

.getAttribute(name)

Ищет именованную запись в .attributes, либо nil.

.setTexture(tex)

Устанавливает текстуру на нижележащий love.Mesh, если он есть.

.dispose()

Сбрасывает ссылку .mesh. three.js здесь освобождает GPU-буферы; меши LÖVE вместо этого собираются сборщиком мусора, так что это существует в основном для того, чтобы код очистки читался одинаково в обоих случаях.

Differences from three.js

  • Нет системы атрибутов на типизированных массивах (setAttribute, BufferAttribute, morph targets, groups). Вершинные данные хранятся в обычной Lua-таблице плюс love.Mesh, построенном импортёром; getAttribute только читает плоскую таблицу по имени, она не строит объекты BufferAttribute three.js.
  • .dispose() просто сбрасывает ссылку — тут нет GPU-буфера, который нужно явно освобождать.
